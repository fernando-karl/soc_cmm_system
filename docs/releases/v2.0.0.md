# 2.0.0 — the real SOC-CMM questionnaire

The questionnaire this project shipped had been reconstructed by hand and
diverged from SOC-CMM® badly enough to misrepresent the framework. This release
generates it from the official workbook instead, moves to **SOC-CMM® 2.4.2
(advanced)**, and translates the whole thing into Portuguese.

## ⚠️ Upgrading from 1.x

**There is no in-place migration.** Question and answer ids from 1.x do not map
onto this release. Seeding never overwrites existing content, so an existing
database keeps its old questionnaire — `scripts/init_db.py` now detects this and
tells you. To move across, export anything you need and rebuild:

```bash
python scripts/init_db.py --recreate
```

## The questionnaire

Aspect names in 1.x appear to have been inferred from the three-letter sheet
codes rather than read from the sheets:

| Code | Official aspect | 1.x shipped |
| --- | --- | --- |
| CST | Customers | **Cost** |
| R&H | Roles and Hierarchy | **Retention & Hiring** |
| DTE | Detection Engineering & Validation | **Data & Technology Exchange** |
| SCM | Security Monitoring | **Service Catalog Management** |
| THR | Threat Intelligence | **Threat Hunting & Research** |

`Results` was also scored as a sixth domain and plotted on the radar chart. In
the workbook it holds the output — Results, NIST CSF Scoring, Results Sharing —
and has no scored questions. SOC-CMM® has **five** scored domains.

| | 1.x | 2.0.0 |
| --- | --- | --- |
| Domains | 6 | **5** |
| Aspects | 30, mostly misnamed | **27**, official names |
| Questions | 97 | **622** |
| Answer options | 12 | **3110** |
| Scorable questions | 11 of 97 | **all 622** |
| NIST mapping | — | **CSF 2.0 per question** |

Every answer option is now that question's own description of what the maturity
level means, taken from the workbook's `_Guidance` sheet, rather than a generic
label. A fully mature SOC scores 5.0/5; 1.x capped it below full marks.

`scripts/extract_soc_cmm.py` regenerates the dataset from any SOC-CMM workbook,
so a future release is a re-run rather than a re-transcription.

## Portuguese

The interface was bilingual; the questionnaire was not. All **1746 distinct
strings** are now translated — 5 domains, 27 aspects, 622 questions, 615
guidance notes and 3110 answer options. Each records its origin in
`dataset/translations/pt_br.json`, so review can be targeted: 28 human, 321
carried over from earlier files, 1397 machine-translated.

**Review of the machine-translated Portuguese is the most useful contribution
available right now** — see [help wanted: review the Brazilian Portuguese
translation](https://github.com/fernando-karl/soc_cmm_system/issues/22) for how to take a piece of it. Reviewing one answer option
can fix dozens of screens, because options are deduplicated and expanded back
across every question that uses them.

### It works on a fresh install

`scripts/init_db.py` created the four translation tables but never loaded
anything into them, so the interface was translated while the questionnaire was
not — a Portuguese user got all 622 questions, their guidance and all 3110
answer options in English. Loading them was a documented manual step the README
never mentioned.

The bootstrap now imports every `dataset/translations/*.json` itself and reports
the translated-question count per language. The import is `INSERT OR REPLACE`,
so it also picks up a corrected translation file without a rebuild.

## Scoring

Scores follow the **official SOC-CMM® 2.4.2 (advanced) workbook**, so a number
from this tool is comparable with a number from the spreadsheet.

Per aspect, over the answered questions with answer `a` in 1..5 and importance
factor `h`, the workbook's `_Output` sheet computes:

```
total = SUM(a × h)      max = SUM(5 × h)      min = SUM(h)
percentage = 100 × (total − min) / (max − min)
```

which is a factor-weighted mean of `(a − 1) / 4`. Subtracting `min` normalises
over the *range* of the scale rather than its top, so **the lowest answer scores
0%** — a SOC with none of a capability reads zero, not a misleading 20%.

| All answers at | Percentage |
| --- | --- |
| level 1 | 0% |
| level 2 | 25% |
| level 3 | 50% |
| level 4 | 75% |
| level 5 | 100% |

Maturity on the familiar 0–5 scale is `5 × percentage / 100`, and a domain is
the plain mean of its aspects — both as the workbook's results sheet derives
them.

### Importance

Each answer carries an importance for this SOC, as the workbook uses it:

| Importance | Factor |
| --- | --- |
| `none` | 0 |
| `low` | 0.5 |
| `normal` | 1 |
| `high` | 2 |
| `critical` | 4 |

A question marked `none` drops out of the score entirely. Pass `importance`
(1–5) to `POST /api/answers`; it defaults to `normal`, which is what every
question ships as in the workbook, so the weighting stays inert until an
assessor sets it. The factor cancels within a single question and across an
aspect of uniform importance, so it only moves the result where an aspect mixes
importances.

An aspect whose every answered question is marked `none` has `SUM(h) = 0` and no
defined percentage. The workbook yields a division error there; this tool stores
no score rather than claiming zero maturity for something never assessed.

**The questionnaire interface has no control for importance yet**, so it is
API-only. Every answer saved from the web interface is `normal`.

Two parts of the workbook are not reproduced here: it tracks completeness
separately from maturity, and it has its own NIST CSF scoring sheet. Each
question still carries its NIST CSF 2.0 mapping in the dataset.

> **Upgrading from 1.x:** stored percentages were computed as `mean(a) / 5`,
> where the lowest answer scored 20%. `scripts/init_db.py` recalculates them
> from the stored answers and says so. Expect percentages to go **down**; the
> raw answers are untouched.

## Security

### Access control

Seven endpoints took no authenticated user and performed no ownership check.
Because customer and assessment ids are sequential integers, anyone who could
reach the server could enumerate and read any tenant's assessment results, and
`POST /api/answers` accepted writes into any assessment. All seven now require
authentication and verify ownership, covered by tests that assert a 403 for a
different tenant and 401 for anonymous callers.

**If you run a deployment older than this release, update.**

### Sessions

Three session settings were hardcoded where no environment variable could reach
them, so the only way to change them was to edit the source:

- The session cookie's `Secure` flag was hardcoded `false`, with a comment
  saying to change it for production. It now follows `ALLOWED_ORIGINS` — on
  when every origin is `https://`, off otherwise — and `COOKIE_SECURE` forces
  it either way, which is what a deployment behind a TLS-terminating proxy
  needs. It is not on by default because a browser never sends a secure cookie
  over plain HTTP, which would break login on `http://localhost`.
- `SameSite` is configurable through `COOKIE_SAMESITE`, still `lax`.
- `ACCESS_TOKEN_EXPIRE_MINUTES` existed but nothing read it. Login issued a
  24-hour token with a 24-hour cookie, and `create_access_token` fell back to
  15 minutes when given no explicit lifetime — three values, none of them
  configurable. Token and cookie now expire together after
  `ACCESS_TOKEN_EXPIRE_MINUTES`, whose default is **8 hours** rather than 24:
  long enough to work through 622 questions, short enough that a stolen cookie
  is not valid for a day.

### Dependencies

- `python-jose` 3.3.0 → 3.5.0, fixing CVE-2024-33663 (algorithm confusion with
  an OpenSSH ECDSA key) and CVE-2024-33664 (JWE decompression bomb).
- `mcp` 1.0.0 → 1.30.0, with `httpx` 0.27.0 → 0.28.1, which it requires. The
  2.x line moved the decorator API off the lowlevel `Server` onto `FastMCP`,
  so staying on 1.x is what keeps the MCP server working.

## Also fixed

- A fresh clone could not be started by following the README. `scripts/init_db.py`
  now builds a working database in one command and is safe to re-run.
- `passlib` was pinned without a `bcrypt` pin, so a fresh install resolved to
  bcrypt 5.x and **no password could be hashed or verified at all**.
- `POST /api/answers` passed an argument `save_answer()` did not accept and
  returned 500 on every call.
- The progress-over-time chart ordered assessments newest-first, drawing an
  improving SOC as a decline.
- `start_mcp_server.sh` pointed at a moved file and never started the server.
- Every `*_pt_br.html` page extended the English base template, so the
  Portuguese interface rendered an English navigation bar and footer.
- Three column-position bugs in the extractor: spreadsheet columns move between
  releases and were read by position, which gave 2.4.2 a bogus NIST mapping and
  silently dropped all 615 per-question remarks.
- `ALLOWED_ORIGINS` defaulted to `http://localhost:8000` while the application
  serves on 8400, so the documented default rejected exactly the browser
  requests it was meant to allow. It now follows `PORT`.
- The MCP server passed `notification_options=None` into `get_capabilities`,
  which reads attributes off it. The old pin tolerated that; any current `mcp`
  raises `AttributeError` before the server accepts a request.
